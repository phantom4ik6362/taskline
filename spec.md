# CLI Task Manager — v1

## Цель

Создать локальное интерактивное CLI-приложение для управления задачами.

Программа должна сохранять состояние между запусками в JSON-файле.

Конкретная архитектура, структура файлов, классы, функции и визуальный дизайн интерфейса спецификацией не задаются.

---

## Данные задачи

Каждая задача содержит:

- body — обязательный текст задачи;
- status;
- created_at;
- deadline — опционально;
- priority — опционально.

### Status

В v1 используются:

- `todo`
- `done`

Новая задача создаётся со статусом `todo`.

Завершённая задача получает статус `done`.

Допустимые статусы должны контролироваться программой.

Пользователь напрямую status не вводит.

---

## Даты

Приложение работает только с датами, без времени суток.

Формат:

`YYYY-MM-DD`

`created_at` содержит дату создания задачи.

`deadline` может отсутствовать.

При создании задачи разрешены:

- сегодняшний deadline;
- будущий deadline.

Deadline в прошлом вводить нельзя.

При некорректном deadline пользователь должен повторно ввести только deadline.

---

## Overdue

`overdue` не хранится как постоянное значение.

Он вычисляется на основании текущей даты.

Правило:

- `deadline < today` → overdue;
- `deadline == today` → не overdue;
- `deadline > today` → не overdue.

Завершённые задачи не рассматриваются как overdue.

---

## Priority

Priority является опциональным.

Допустимые значения:

`1–10`

где `10` — максимальный приоритет.

Пустой ввод означает отсутствие priority.

Невалидный ввод, включая значение вне диапазона или нечисловое значение, не должен сбрасывать весь процесс создания задачи.

Пользователь повторно вводит только priority.

---

## Команды

Основные команды:

- `add`
- `list`
- `complete`
- `history`
- `exit`

Алиасы:

- `add` → `ad`
- `list` → `ls`
- `complete` → `cp`
- `history` → `hs`

Конкретный формат парсинга команды определяется разработчиком.

---

## UI state

Приложение имеет два режима интерфейса:

### LIST

Основной режим.

Показывает активные задачи.

Разрешены:

- add;
- complete;
- history;
- list;
- exit.

### HISTORY

Read-only режим.

Показывает завершённые задачи.

Разрешены:

- list;
- history;
- exit.

`add` и `complete` должны быть отклонены понятной ошибкой.

После ошибки пользователь остаётся в HISTORY.

---

## Поведение view-команд

При запуске приложение автоматически открывает LIST.

`history` переключает интерфейс в HISTORY.

`list` переключает интерфейс в LIST.

Если пользователь вызывает уже активный view:

- `list` в LIST;
- `history` в HISTORY;

команда является no-op: состояние интерфейса не меняется и дополнительное действие не требуется.

---

## Add

Команда доступна только в LIST.

Процесс создания задачи запрашивает:

1. body;
2. priority;
3. deadline.

Body обязателен.

Пустой body → ошибка → повторный ввод только body.

Priority и deadline опциональны.

При ошибке любого отдельного параметра пользователь повторно вводит только этот параметр.

После успешного создания задача должна быть сохранена.

После завершённой команды интерфейс перерисовывается.

---

## List

LIST показывает только активные задачи.

Каждая видимая задача получает временный пользовательский номер:

`1, 2, 3...`

Этот номер:

- не является постоянным ID задачи;
- не обязан храниться в JSON;
- существует только относительно текущего отображённого списка.

Конкретный внешний вид интерфейса спецификацией не задаётся.

Пользователь должен иметь возможность понять:

- номер задачи;
- body;
- priority, если есть;
- deadline, если есть;
- overdue-состояние, если применимо.

---

## Сортировка LIST

Активные задачи отображаются группами в следующем порядке:

1. overdue-задачи;
2. задачи с будущим deadline и priority;
3. задачи с будущим deadline без priority;
4. задачи без deadline с priority;
5. задачи без deadline и без priority.

Внутри групп, где используется priority, более высокий priority должен иметь больший приоритет при отображении.

Для задач, полностью равных по критериям сортировки, дополнительный порядок не гарантируется.

---

## Complete

Команда доступна только в LIST.

Пользователь обращается к задаче по номеру строки, который видит в текущем LIST.

Например:

`complete 2`

означает завершение второй задачи именно в текущем отображённом списке.

Программа должна гарантировать, что номер соответствует той же сортировке, которую видит пользователь.

После успешного complete:

- задача получает status `done`;
- изменения сохраняются;
- пользователю показывается подтверждение;
- LIST перерисовывается;
- завершённая задача больше в LIST не отображается.

Если номер отсутствует или некорректен:

- показать понятную ошибку;
- не менять данные;
- снова ожидать команду.

---

## History

HISTORY показывает только задачи со status `done`.

Режим read-only.

Задачи из HISTORY нельзя изменять в v1.

Поддержка reopen/delete в v1 отсутствует.

---

## Delete

Отдельной команды удаления в v1 нет.

Если задача больше не актуальна, пользователь может завершить её, после чего она попадёт в HISTORY.

---

## Persistence

Состояние хранится локально в JSON.

Конкретная JSON-структура определяется разработчиком.

После каждого успешного изменения данных:

- add;
- complete;

состояние должно сохраняться на диск.

При `exit` состояние также сохраняется перед завершением программы.

---

## Поведение storage при запуске

### JSON-файл отсутствует

Программа должна создать корректное пустое хранилище и продолжить работу.

### JSON-файл существует, но пустой

Программа должна привести его к корректному пустому JSON-состоянию и продолжить работу.

### JSON-файл содержит невалидный JSON

Программа не должна молча затирать данные.

Необходимо показать ошибку запуска и остановить приложение.

---

## Ошибка сохранения

Если изменение данных в памяти произошло, но запись JSON завершилась ошибкой:

- пользователь должен увидеть понятную ошибку;
- программа не должна сообщать, что операция успешно сохранена.

Rollback состояния памяти в v1 не является обязательным требованием.

---

## Terminal UI

После завершённых команд приложение может очищать терминал и полностью перерисовывать текущее view.

При ошибке отдельного поля внутри `add` экран не очищается: показывается ошибка и повторно запрашивается только проблемное поле.

Конкретный дизайн терминального интерфейса остаётся за разработчиком.

Оцениваться должна usability, а не совпадение с заранее заданным макетом.

---

## Usability requirements

Пользователь должен без чтения исходного кода понимать:

- в каком view он находится;
- какие задачи активны;
- какие задачи завершены;
- какой номер использовать для `complete`;
- priority;
- deadline;
- overdue-состояние;
- какие команды доступны;
- почему конкретный ввод был отклонён.

---

## Не входит в v1

Не требуется:

- delete;
- reopen;
- постоянный task ID;
- время суток в deadline;
- несколько пользователей;
- база данных;
- сеть/API;
- authentication;
- GUI;
- сторонние библиотеки;
- обязательный конкретный визуальный стиль CLI.

---

# Definition of Done

Продукт считается готовым, если:

1. Программа запускается как интерактивный CLI.
2. LIST автоматически показывается при старте.
3. `add/ad` создаёт корректную задачу.
4. `list/ls` показывает активные задачи в требуемом порядке.
5. `complete/cp` завершает именно выбранную пользователем видимую задачу.
6. `history/hs` показывает завершённые задачи.
7. Ограничения команд текущего view соблюдаются.
8. Deadline и priority валидируются.
9. Overdue вычисляется корректно по текущей дате.
10. Данные сохраняются между запусками.
11. Missing/empty/corrupt storage обрабатывается согласно спецификации.
12. Ошибки пользователя не приводят к traceback в обычных ожидаемых сценариях.
13. После перезапуска состояние соответствует последнему успешно сохранённому состоянию.
14. Интерфейс остаётся понятным без требования совпадать с конкретным макетом.
